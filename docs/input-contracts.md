# Input contracts (1.0.0)

The JSON schemas in `schemas/` define normalized exports. Run the bundled synthetic export before adapting customer exports. This prototype reads one inventory JSON, one API evidence JSON and one sources JSON; it never connects to SAP. Inline ABAP is scanned as data using an intentionally incomplete lexical heuristic.

- Inventory identifies source and target family, edition, release and FPS; applications, ABAP text, coverage, usage, declared dependencies, application edges, datasets and screens. `coverage_complete` is an exporter assertion; CoreLift still requires architect/ATC review. SAP extraction/parsing adapters are not implemented.
- Screens preserve PBO/PAI, validation, authorization, value help, locking and errors. Moving Dynpro/WebDynpro to Fiori/CAP requires UI behavior reconstruction, not copying a screen definition. Empty behavior arrays mean the exporter has provided no behavior evidence.
- API evidence carries classification state, release contract (C0/C1/C2), supported operations, endorsed remote operations, remote pathway, source ID and immutable snapshot revision. Customer snapshots require a 40-character Git commit for the version-specific Cloudification Repository. `latest` or a mismatched edition/release/FPS yields unknown classifications. A hash alone proves no correctness: the exporter/architect must verify the snapshot, operation-specific API contract, technology and endorsed pathway. `exported-unverified` explicitly records that CoreLift has not validated SAP availability and yields unknown effective classifications in this prototype; claimed states remain visible. Verified customer evidence ingestion is a future capability. Direct table/technology access cannot inherit a C2 remote API contract, and dynamic calls always remain unresolved.
- Synthetic inventory and synthetic evidence must agree; individual record verification flags must agree. All `SYN_*` API identifiers are fictional. A generic policy link is never proof that a fictional or customer API exists.
- Dataset metadata separates ERP ownership, extension ownership and reference cache; classification or owner may be `unknown`. No customer rows are needed for assessment. Ownership, retention/residency, configurations/attachments, keys, authorizations, currency/units/timezones, initial/delta volumes and semantic thresholds require review before migration.
- Source records identify URL, checked date, revision and scope. Living-document policy revisions are distinct from the pinned API snapshot. Run records hash normalized JSON inputs; reformatting is immaterial. Preserve original export hashes separately for customer audit.

Inputs reject unknown fields, invalid types, dangling graph references and duplicate IDs. CLI JSON is limited to 5 MB per regular local input file using a bounded read; very large exports need a future bounded ingestion adapter. The scanner handles selected static table operations/function calls, multiline dynamic function calls and conservatively flags CALL METHOD dispatch. Dynamic calls recognized by these heuristics stay unresolved. It is not an ABAP parser and cannot establish coverage for all expressions/macros/SQL forms. Report JSON includes decisions, dependencies, candidates, unknowns, draft plan, source records and deterministic input hashes. Assessment runs do not write files unless an output folder is explicitly supplied.
