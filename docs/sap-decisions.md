# SAP decisions and evidence boundaries

Checked 2026-10-02. This is a policy map, not an API availability catalog.

SAP's [current extensibility guidance](https://learning.sap.com/courses/practicing-clean-core-extensibility-for-sap-s-4hana-cloud/explaining-extensibility-model-best-practices_e290f382-800e-40ef-a203-85a13115f487) uses levels A–D: released, nominated classic, internal, not-recommended. The weakest dependency/technology governs. CoreLift estimates dependency-level candidates and leaves final technology/functional assessment to a reviewer. Legacy tiers may be ingested by a later adapter; they are not the new decision model. Existing wrappers do not automatically need rewriting, and do not erase B/C/D dependencies.

Pin the [Cloudification Repository](https://github.com/SAP/abap-atc-cr-cv-s4hc) to target edition/release/FPS and immutable commit. Read SAP [API release contracts](https://help.sap.com/docs/abap-cloud/abap-development-tools-user-guide/released-apis): C0 is extension, C1 local use, C2 remote use. A released local contract alone cannot justify BTP remote access. Availability, operation coverage, transactional semantics and technology eligibility are separate facts. No API match means unknown until investigated, rather than proof of impossibility.

If no released capability covers the use case, investigate standard replacement, key-user/developer extension, an applicable SAP-nominated classic API, a narrow wrapper under [API Enablement Guidelines](https://www.sap.com/documents/2023/05/b0bd8ae6-747e-0010-bca6-c68f7e60039b.html), or governed retention. Wrapper review needs an owner, expiry, upgrade/replacement trigger, ATC and ABAP Unit evidence, authorization/locking/transaction tests and a narrow supported caller contract. C-level changelog/impact support is target-dependent; do not assume universal tooling. Public edition does not inherit private/on-premise classic/internal exceptions. Not-recommended dependencies need redesign. The archived tier2 RFC proxy is not a maintained dependency.

ECC cannot run on-stack ABAP Cloud. Supported S/4HANA private/on-premise starts at 2022; meeting the version floor is only one eligibility condition. ERP conversion/remediation is distinct from moving extension logic to BTP. SAP's Custom Code Migration Agent/ADT workflows address a scoped ECC-to-S/4 workstream, and generic MCP availability does not prove each host can run the same ADT workflow.

[SAP API policy](https://help.sap.com/doc/sap-api-policy/latest/en-US/API_Policy_latest.pdf) constrains autonomous sequencing to SAP-endorsed pathways. No unconstrained RFC/OData proxy or claim of certified compliance belongs in CoreLift. The [CAP runtime MCP adapter](https://cap.cloud.sap/docs/guides/ai/cap-mcp) supports custom CAP services and explicitly forbids proxying SAP Application APIs. The [CAP development MCP](https://github.com/cap-js/mcp-server) is a separate development tool. Future connectors must declare a narrow supported capability and evidence of its allowed pathway.

Keep ERP authoritative. Separately assess extension-owned Z data and minimal reference caches. SAP Migration Cockpit is not a generic Z-table-to-BTP transfer engine. Before writes: owner/field scope, retention/residency, semantic mapping, supported extract/load, initial-plus-delta plan, rejects/idempotency, counts and business totals, cutover freeze, reconciliation and rollback proof. Rebuild Dynpro/WebDynpro behavior including PBO/PAI validations, authorizations, value help, locks and errors; do not promise screen conversion.
